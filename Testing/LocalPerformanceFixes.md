# 本地常驻性能修复验收

基线：`3783669`；2026-10-10 最小移植。测试包：`dist/performance-fixes-20261010/Remote Mic.app`。

## 范围与准备

仅修复监听端口释放、空闲自造音频重配、共享 HID 权限查询及休眠蓝牙扫描。未引入上游新功能、私有依赖、异步音频重配或新的录音实验。

退出其他 Remote Mic 实例，启动上述包。确认蓝牙、输入监控和辅助功能权限；微信输入法沿用原配置，麦克风为 MiRemoteV 2ch。旧包保留在 `dist/audio-optimizations-20260907/Remote Mic.app`，可以退出新包后切回对照。

## 验收步骤

| 场景 | 操作 | 预期与失败判定 |
| --- | --- | --- |
| 正常语音 | 按住即说 5 秒，松开，重复 5 次；更换前台输入框再试 | 首次就识别、尾字正常；需重按才成功为失败 |
| 续接 | 50～60 秒松键，2 秒内重按，连续 3 段 | 微信保持同一会话，每段倒计时重置，桌面提醒正常；重复 Fn、断流或缺字为失败 |
| 续接超时 | 50～60 秒松键后不重按 | 2 秒后正常结束；下一段能重新输入 |
| 空闲性能 | 连接后关设置窗口，静置 5 分钟；记录 App、WindowServer 的 CPU 和内存 | 不出现约每秒一次的引擎重配循环；不能把正常硬件/唤醒恢复算作循环 |
| 多次重连 | 让遥控器断连再连接，重复 10 次，每次验证语音与上下键 | 功能正常，界面不越来越卡；全局监听端口计数需有权限的独立工具验证，不能以 App CPU 正常代替 |
| 音频变化 | 空闲和说话时分别连接/断开耳机，随后开始新语音 | 真实路由变化仍恢复，首次语音可用；音频恢复被空闲判断吞掉为失败 |
| 休眠恢复 | 空闲熄屏/睡眠 2 分钟后唤醒，第一次就按住说话 | 挂起后不再主动扫描/安排重连；唤醒后恢复语音与按键 |
| 休眠中断连 | 遥控器处于搜索/重连时熄屏；唤醒后重新连接 | 挂起时取消连接任务，唤醒后补一次连接周期，不需重启 App |
| 续接与熄屏交错 | 在续接等待时熄屏，再重按或等超时 | 已 ready 的连接与 PCM 仍可工作；2 秒等待不提前释放 Fn 或音频 |
| 权限撤销 | 在系统设置中撤销输入监控，再恢复 | 约 1 秒内清理按键状态；恢复后按原流程重新启用映射，不能留下卡住的按键 |

## 日志与验证边界

- 日志：`~/Library/Logs/RemoteMic/runtime.log`，记录测试起止时间。重点看 `AUDIO RECOVERY ignored`、`AUDIO REBIND`、`BLE SYSTEM_SUSPENSION`、`BLE SCANNING`、`continuation_`。
- `BLE SYSTEM_SUSPENSION paused ready_preserved=true` 不会主动断开就绪连接；屏幕、系统睡眠与会话挂起全部解除后才恢复连接工作。
- 已运行现有 196 项 Swift 回归及 42 项项目自检，全部通过；临时定向验证覆盖 6 项音频、权限、休眠策略，验证代码不保留在仓库。当前测试进程不能创建 event tap，端口真实计数对照跳过；不将此项表述为通过。
- Release 构建、资源与 ad-hoc 签名验证只能证明包可构建；真实微信续接、首次声音、CPU/内存收益、整夜睡眠和 WindowServer 长跑仍待用户验收。
